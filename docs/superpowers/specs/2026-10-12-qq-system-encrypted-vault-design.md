# QQ SYSTEM 加密隔离设计

## 目标

QQ 使用结束后，不能再通过找到隔离文件、将其改名为 `QQ.exe` 并移回安装目录来绕过限制。隔离物的路径和名称不出现 `QQ`、`Tencent`、`MashiroBot`、`vault` 或 GUID 形式。合法使用、临时放行、到期重新隔离、故障恢复和卸载恢复仍然可用。

本设计不把文件写进 `Windows`、`System32`、`WinSxS`、驱动仓库或其他由 Windows 管理的目录，也不伪装成可能被系统加载的 DLL。这样避免系统维护、杀毒软件、组件扫描或误加载破坏隔离物及操作系统。

## 方案

采用由 SYSTEM 身份保护的加密容器，而不是保留一份可直接运行的改名 EXE。

- 隔离根目录位于 `ProgramData` 下的应用自管区域，安装时生成不带语义且不是 GUID 格式的目录和缓存文件名。实际路径不写入 `last-status.json`，也不出现在普通状态命令输出中。
- `QQ.exe` 使用随机 256 位 AES-GCM 密钥加密。每次隔离生成新的密钥和 96 位 nonce。
- AES 密钥通过 Windows DPAPI `CurrentUser` 作用域、由 SYSTEM 账户封装。普通用户即使找到并复制容器，也不能通过改扩展名得到可运行程序。
- 容器保存格式版本、DPAPI 密钥封装、nonce、认证标签和密文；明文 SHA-256 与腾讯签名信息继续保存在现有保险库记录中。
- 隔离目录关闭继承并仅授予 SYSTEM 完全控制。管理员仍可通过取得所有权进行应急处理，但这需要明确提权操作，不能通过资源管理器中的一次改名完成。

加密是主要防线；目录和名称只用于减少偶然发现，不把“别人不知道路径”当作安全保证。

## 状态与数据边界

现有 `installed_executable_vault` 记录继续作为恢复状态的权威来源，但增加容器格式标识。数据库内部可以保存实际路径，面向普通用户的状态对象只返回：

- `state`
- `formatVersion`
- `sha256`
- `signer`
- `protectedAt`、`restoredAt`、`updatedAt`
- `error`

不返回 `vaultPath`、DPAPI 数据或容器文件名。`originalPath` 只在需要诊断安装位置时由管理员状态输出提供；普通缓存和插件预检不依赖它。

运行时分工保持明确：

- `MashiroBot-QQSession-Reconcile` 以 SYSTEM/Highest 运行，负责加密、解密、迁移和恢复。
- `MashiroBot-QQSession-Launch` 继续以交互用户/Limited 运行，只启动已经恢复并验证的 `QQ.exe`，不接触密钥或容器。
- 普通 Node 插件只触发 SYSTEM 任务并读取脱敏状态。

## 隔离流程

1. 停止精确匹配安装路径的 QQ 进程。
2. 确认源文件是普通文件、不是重解析点，且 SHA-256 和腾讯 Authenticode 签名有效。
3. 在隔离根目录生成临时容器，使用 AES-GCM 加密，并通过 SYSTEM DPAPI 封装密钥。
4. 将容器解密到受控临时文件，重新验证 SHA-256 和腾讯签名。
5. 写入 `protecting` 记录后删除安装目录中的明文 `QQ.exe`，再将记录切换为 `protected`。
6. 清理中间明文和过期容器。日志及状态不记录实际隔离路径。

任何一步失败都不能删除唯一有效副本。只有加密容器完成解密校验后才允许删除源文件。

## 恢复流程

1. 仅 SYSTEM 任务读取活动记录并验证容器结构和 AES-GCM 认证标签。
2. 解密到 QQ 安装目录中的随机临时文件。
3. 校验明文 SHA-256、普通文件属性及腾讯签名。
4. 原路径为空时，使用同卷原子移动生成 `QQ.exe`；若原路径被不同文件占用则保持冲突状态，不覆盖。
5. 验证最终 `QQ.exe` 后把记录切换为 `available`，再删除加密容器。

如果原路径已经存在同哈希且签名有效的 QQ，则沿用现有恢复规则，将其视为已恢复；不同文件继续作为硬冲突处理。

## 旧保险库迁移

安装或首次 SYSTEM 对账时检查当前活动记录：

- 若记录指向旧版明文保险库，先验证其哈希和腾讯签名，再生成并验证新版加密容器。
- 数据库切换到新容器后才删除旧版明文文件。
- 如果迁移中断，恢复逻辑优先选择能通过完整校验的副本；同时存在时优先完成加密迁移并清理旧明文。
- 若任何校验失败，保留旧文件及原记录并报告错误，不把失败状态伪装成已保护。

## 临时放行与卸载恢复

现有 `C:\Users\Mashiroyes\qq-temporary-release.ps1` 不能再读取 `last-status.json` 中的 `vaultPath` 并直接复制文件。它改为：

1. 写入有明确过期时间的人工授权。
2. 触发固定参数的 SYSTEM 恢复任务。
3. 等待脱敏状态确认 `qqInstalled=true`、哈希及签名验证通过后再报告成功。
4. 到期任务先撤销授权，再触发 SYSTEM 重新隔离并确认 `state=protected`。

卸载/维护恢复同样通过不向普通用户授予运行权限的 SYSTEM 恢复任务完成。不能提供一个普通用户可直接启动、且不检查授权时间的解密任务。

## 星期日四小时特殊命令

增加固定命令 `周末玩QQ4h`，它属于正常 QQ 会话状态机的特殊入口，不复用无会话记录的人工临时放行脚本。

- 使用 `Asia/Shanghai`（Windows `China Standard Time`）判断收到命令的本地日期。
- 只有收到命令的时刻仍为星期日才接受；星期六及星期一至星期五都拒绝，并且不能恢复 `QQ.exe`、写入有效授权或撤销客户端屏障。
- 接受后固定放行 240 分钟，从确认时刻开始计算。该会话允许跨越星期一 00:00，也允许跨越通常的 22:00 截止时间；例如星期日 21:00 接受后，截止时间为星期一 01:00。
- 每个上海本地星期日日期只能成功启动一次特殊会话。次数在会话完成恢复、授权并原子切换到 `playing` 时消耗；解析拒绝或启动技术失败不消耗次数。
- 一旦特殊会话成功启动，当天即使主动提前结束、正常结束或使用现有恢复功能，也不能创建第二个特殊会话。并发请求必须由数据库事务或唯一约束保证最多一个成功。
- 特殊命令不接受自定义分钟数，也不扩大普通 `玩QQ N分钟` 命令的时间窗口。
- 活动会话、并发请求、失败回滚和目标路径冲突继续沿用现有规则。特殊会话结束后仍执行固定 60 分钟冷却，并由 SYSTEM 任务重新生成加密隔离容器。
- 会话记录保存明确的 `windowPolicy=sunday-4h`（或等价枚举字段），worker 只根据该受信字段绕过普通 `[12:00, 22:00)` 窗口，不能根据任意 240 分钟请求自行推断为特殊会话。

解析器、帮助文本、模型、存储层和 PowerShell worker 必须使用同一规则。测试覆盖星期日 21:00 至星期一 01:00、星期日 23:59 起完整 240 分钟、星期一 00:00 拒绝、星期六拒绝、同一星期日第二次及并发请求拒绝、启动失败后允许重试，以及特殊会话结束后的 60 分钟冷却和加密隔离。

## 崩溃恢复规则

- `protecting` 且源文件与有效容器同时存在：未授权状态下完成源文件删除并转为 `protected`。
- `protecting` 且只有源文件：回到 `available`，不宣称已隔离。
- `protecting` 且只有有效容器：转为 `protected`。
- `restoring` 且有效原文件与容器同时存在：转为 `available` 并清理容器。
- `restoring` 且只有有效容器：重试恢复。
- 任何容器认证、哈希或签名失败：转为 `invalid`，保留可用副本并阻止启动。

所有状态文件继续通过同目录临时文件加 `[IO.File]::Move(..., $true)` 原子替换。

## 验收标准

1. 结束一次测试会话后，安装目录不存在 `QQ.exe`；隔离物不是 PE 明文，复制并改名为 `QQ.exe` 后无法通过哈希、签名及启动验证。
2. 常规状态与 `last-status.json` 不含 `vaultPath`、隔离根目录或容器文件名。
3. 合法会话由 SYSTEM 解密恢复，最终文件哈希与隔离前一致、腾讯签名有效，并能由交互用户任务启动。
4. 会话结束或临时放行到期后重新生成新版加密容器，明文 `QQ.exe` 再次消失。
5. 当前旧版明文保险库被迁移；旧路径不再保留可直接改名运行的 QQ 明文副本。
6. 容器任一字节被篡改、DPAPI 解封失败或目标路径存在不同文件时，恢复失败且不覆盖目标。
7. 模拟每个关键写入点中断后，至少保留一份可验证副本，并能由下一次 SYSTEM 对账收敛到 `protected` 或 `available`。
8. 仓库测试通过；源 worker 与已部署 worker 哈希一致；SYSTEM 对账任务返回成功；最终状态同时满足 `VaultState=protected`、`VaultReady=true`、`ClientBarrierActive=true`、`WebsiteBlockActive=true`。
9. `周末玩QQ4h` 仅在上海本地时间星期日接受，并完整授权 240 分钟；跨星期一和跨 22:00 不提前结束，星期六与星期一请求均保持全部拦截，结束后执行 60 分钟冷却及加密隔离。
10. 同一个上海本地星期日只能成功启动一次特殊会话；第二次、提前结束后的再次请求及并发重复请求均被拒绝，启动技术失败则不错误消耗当日次数。
